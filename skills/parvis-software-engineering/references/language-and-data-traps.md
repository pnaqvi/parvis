# Language and data traps

*Load-on-demand companion to `parvis-software-engineering`. Depth on Java, Python and Rust, then the relational, document and graph material and the cross-store concerns. Every version-dependent claim below was checked against the vendor's own documentation on 2026-09-20 and carries `[verified 2026-09-20]` with its source, or `[model]`, unverified as of training data, where the check could not be made (T2). Runtimes move faster than this file, so any claim older than one JDK, CPython or engine release cycle is re-verified at the next Parvis release, and a claim naming a version older than the one deployed is treated as unchecked until it is re-read. Ask for the exact runtime, driver and engine versions before a claim becomes a finding, since the version decides which line applies.*

## 1. Java

Virtual threads are final in Java 21 `[verified 2026-09-20, openjdk.org/jeps/444]`, and the trap is the code around them rather than the feature. A virtual thread pinned inside a `synchronized` block blocks its carrier, which made `synchronized` critical sections holding IO a throughput cliff in 21. JEP 491 relieved it in JDK 24 by letting a virtual thread hold a monitor independently of its carrier `[verified 2026-09-20, openjdk.org/jeps/491, closed and delivered in 24]`, and the JEP's own wording is "nearly all cases", since class loading and class initializers still pin, so the pinned-thread trace keeps earning its place after the upgrade. Pooling stays wrong, since a pool rations a scarce resource and virtual threads are not scarce, so a fixed pool in front of them reimposes the limit the migration was meant to remove. Anything keyed on thread identity breaks, meaning `ThreadLocal` caches sized for a pool and per-thread connection reuse.

Read for double-checked locking without `volatile`, which is broken on the Java memory model in every version. Read for `SimpleDateFormat` shared across threads, and for `LocalDateTime` on a persisted field where an `Instant` was meant, since the first loses the zone. Read for `parallelStream()` on the common ForkJoinPool, which couples unrelated workloads and inverts under IO.

Illegal reflective access to JDK internals is denied by default from Java 16 `[verified 2026-09-20, openjdk.org/jeps/396]`, so a library that worked on 8 or 11 can fail at startup after an upgrade rather than in test. Serialization filters, the removal of the SecurityManager and the module system each break a different old habit, so an upgrade review reads the release notes of every intermediate version, not only the target.

## 2. Python

The GIL is the frame for every concurrency question, and since 3.14 the question is which build is deployed rather than which version. The free-threaded build was experimental in 3.13 and became supported, while staying a separate non-default build, in 3.14 under PEP 779 `[verified 2026-09-20, peps.python.org/pep-0779, status Final]`. The check is `sys._is_gil_enabled()`, added in 3.13 `[verified 2026-09-20, docs.python.org sys]`, so a claim that a service now scales across cores is settled by running it rather than by reading a version string. Price it before anyone adopts it. PEP 779 puts the single-threaded penalty against the with-GIL build at around ten percent on the pyperformance benchmarks, nearer three percent on macOS, and the harder cost is the C-extension gap, since a free-threaded deployment is only as free-threaded as its slowest dependency, which is the real reason a change-controlled estate is not there yet. The GIL-era guidance stays as the default rather than the only option, so CPU work belongs in processes and IO work in threads or asyncio, and the common defect is a blocking call inside a coroutine, a synchronous driver or a CPU loop, which stalls the event loop and shows up as latency on every unrelated request.

Process model traps follow the start method, and the default moved. Python 3.14 changed the POSIX default from `fork` to `forkserver` `[verified 2026-09-20, docs.python.org multiprocessing, "Changed in version 3.14"]`, and macOS has defaulted to `spawn` since 3.8 `[verified 2026-09-20, same page]`. On 3.13 and earlier, or anywhere `fork` is still selected explicitly, the old traps hold, so `fork` shares memory copy-on-write and a large parent heap is touched by reference counting until the children grow anyway, and forking a process that already holds locks, threads or open connections deadlocks in ways that reproduce only under load. On 3.14 the trap inverts. `forkserver` and `spawn` inherit no unnecessary resources, meaning no open database connections, no sockets, no module-level globals mutated after import and no preloaded state, so code that quietly relied on inherited parent state breaks on the upgrade with no code change, no compile error and often no exception until the first child does real work. Read for connection pools, clients, caches and credentials built at module import and used from children, and for a preload-then-fork worker model that depends on that inheritance.

Read for mutable default arguments, for bare `except` swallowing `KeyboardInterrupt` and `SystemExit` where `except Exception` was meant, and for `datetime.utcnow()`, which is deprecated from 3.12 in favor of a timezone-aware `datetime.now(timezone.utc)` `[verified 2026-09-20, docs.python.org datetime]` and which silently produces naive datetimes that compare wrongly against aware ones. Read for float arithmetic on money where `Decimal` was meant. Read for type hints treated as enforcement, since they are documentation unless a validator runs. Dictionary insertion order is part of the language spec from 3.7 `[verified 2026-09-20, docs.python.org whatsnew 3.7]`, so ordering assumptions are safe there and unsafe on sets.

## 3. Rust

The borrow checker removes the data race, not the deadlock, the leak or the logic error, so the hunt moves to async and to lock discipline. Holding a `std::sync::Mutex` guard across an `.await` is the signature defect, since the guard is held while the task is parked and another task on the same runtime thread can block on it. Cancellation is the second, since dropping a future at an await point abandons whatever it had half-done, so any sequence that must complete needs its own commit point.

Blocking inside an async runtime starves the executor, and the symptom is a service that looks idle while requests queue, so read for synchronous file, database or crypto work on the async path. Read for `Arc<Mutex<...>>` around a hot structure, which trades the data race for contention, and for locks taken in different orders on two paths.

Integer overflow panics in debug builds and wraps two's complement in release, which is stable behavior rather than a version trap `[verified 2026-09-20, doc.rust-lang.org book, ch. 3.2]`, so arithmetic on untrusted sizes is a release-only wrong answer. The lever is `overflow-checks = true` in the release profile, whose cost is workload dependent and should be measured on the service's own arithmetic-heavy paths rather than assumed `[model]`, unverified as of training data. Reference cycles through `Arc` leak, since there is no cycle collector, and `Weak` is the fix. Read for `unwrap` and `expect` on library paths, for panics inside a worker where the abort policy turns a recoverable request into a process restart, and for `?` propagating through an erased error type until the context needed to triage is gone. Every `unsafe` block and FFI boundary is a defect candidate, since that is where the guarantees stop.

## 4. Relational stores

The index that exists and the index the query uses are different questions, so read the query plan rather than the schema. A composite index serves predicates on its leading columns, which is the right default heuristic rather than an absolute, since skip scan lets later columns be used when an early one is unconstrained and has few distinct values, available in PostgreSQL from 18 `[verified 2026-09-20, postgresql.org 18.0 release notes, 2025-09-25]` and in Oracle and MySQL 8.0 for longer `[model]`. An index on a column wrapped in a function is not used unless the index is expressed the same way, and low-selectivity predicates read as a scan whatever the index says. Locking defects concentrate in long transactions, meaning a transaction held open across a remote call or a user think-time, which blocks writers and, under MVCC, holds back cleanup until the store degrades.

Isolation level is the assumption most often unstated. Read committed is the default in PostgreSQL and Oracle, while InnoDB defaults to repeatable read `[verified 2026-09-20, postgresql.org transaction-iso, docs.oracle.com database concepts 19c, dev.mysql.com InnoDB isolation levels]`, so the same code moved between engines changes correctness rather than performance. Snapshot isolation permits write skew, so any invariant spanning rows that a check-then-write protects needs serializable isolation or an explicit row lock, and the review names which. Schema change is expand then migrate then contract, never a rename in one release, and any DDL that rewrites a large table names the lock it takes and the version that avoids it.

## 5. Document stores

Denormalization is priced by the document size limit and by write amplification. An embedded array that grows per event is the class defect, since the document is rewritten on every append, indexes on the array grow with it, and the ceiling arrives as a hard failure rather than slow degradation, at 16 MiB per document in MongoDB `[verified 2026-09-20, mongodb.com manual reference limits]`. Read for arrays with no bound, for queries filtering on fields no index covers, and for aggregation pipelines whose first stage is unfiltered.

Multi-document transactions need `featureCompatibilityVersion` 4.0 on a replica set and 4.2 on a sharded cluster `[verified 2026-09-20, mongodb.com manual core transactions]`, so the first review question is the FCV rather than the binary version. The cost is not flat, and flattening it is where the folklore starts. A transaction inside one replica set is comparatively cheap, while the distributed case crossing shards is the expensive one, and MongoDB's own text is worth handing to the team, "In most cases, a distributed transaction incurs a greater performance cost over single document writes, and the availability of distributed transactions should not be a replacement for effective schema design." So the review question is whether the transaction crosses a shard, and a design needing cross-shard transactions routinely is usually a relational design in the wrong store. Schema-on-read means every consumer is a migration, so a version field in each document plus readers that tolerate the previous two shapes is the honest pattern.

## 6. Graph stores

The graph earns its place when traversal depth is variable and the path itself is the answer. Fixed two-hop joins are a relational problem, and saying so is often the most useful finding. Supernodes are the class defect, meaning a node whose degree grows with the tenant or with time, which turns a bounded traversal into a scan and creates write contention on a single hot node. Read for traversals with no depth bound, no result limit and no anchored start node, since index-free adjacency only helps once the start set is small. Migration is expensive, since a property or label change is a full traversal, so schema decisions here are closer to one-way doors.

## 7. Across stores

Any write to two stores is a partial-failure candidate. The outbox, written in the same transaction as the business row and published by a separate reader, is the default, with an idempotent consumer keyed on the event ID. A reconciliation job that finds and reports divergence is part of the design, and one that names no reconciliation is incomplete whatever the transaction story claims. Cross-store schema evolution is versioned at the payload, not at the code, so both directions are tested, since rollback reads the new shape with the old code.

## 8. Other languages

The org runs more than these three. Where the code is Go, TypeScript, C#, Kotlin or C++, this skill reasons from first principles rather than pretending to a trap list it does not hold, working from the memory and concurrency model, how errors propagate, how resources are released and where the version changes behavior. It asks for the runtime and framework versions first, and says plainly that the finding rests on structure rather than on a known trap.
